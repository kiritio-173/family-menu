# 当前权限模型收尾与发布实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans (recommended) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 以当前工作树为唯一事实来源，完成管理员、家庭管理员、普通成员和访客的使用逻辑，验证前后端权限一致，再生成便携版并提交推送。

**Architecture:** 服务端是最终权限裁判，前端只负责根据身份隐藏不应出现的入口和给出下一步提示。权限分为三层：全局管理口令对应超级管理员，家庭管理员由一个家庭中的一个或多个 owner 成员组成，成员身份凭证换出设备令牌；未认领身份的访客只能使用公开的日常入口，不能写入带作者归属的私菜。用户可见的登录 ID 与内部成员 ID 分离：登录 ID 支持字母、数字和汉字，内部 ID 仍使用不可变的随机值；验证口令支持一般文本，不限制为纯数字 PIN。状态接口按当前家庭过滤普通用户数据，管理会话才可读取跨家庭管理数据。

**Tech Stack:** Node.js 原生 HTTP 服务、原生 JavaScript 单页前端、JSON 文件数据、PowerShell、Git、现有接口自检和便携版冷启动自检。

## 权限与使用规则

| 身份 | 可以做 | 不可以做 |
| --- | --- | --- |
| 访客 | 查看共享菜单；点餐；库存；本周计划；留言和菜品互动；提交加入家庭申请 | 新增带作者归属的私菜/私有分类；改共享菜单；更新做饭状态；删除或清空点餐；家庭、成员、设置、备份、上传和 AI 管理 |
| 普通成员 | 访客全部能力；查看当前家庭私菜；新增、修改、删除自己添加的私菜和私有分类；维护自己的显示名、登录 ID 和个人密码 | 修改共享菜单；修改别人添加的私菜；更新做饭状态；管理家庭成员、管理员角色、家庭口令、系统设置、备份、上传和 AI |
| 家庭管理员 | 一个家庭中可以有多个；管理本家庭共享菜单、共享分类、本家庭全部私菜、成员和加入申请；更新本家庭点餐做饭状态；维护本家庭名称和图标；新增/撤销其他家庭管理员，但不能把最后一名管理员撤掉 | 修改其他家庭；修改全局设置、全局备份和 AI（除非同时是超级管理员） |
| 超级管理员 | 管理所有家庭、共享菜单、成员、做饭状态、系统设置、备份、上传和 AI；批准家庭状态升级 | 无业务限制，但服务端仍需校验请求数据归属 |

补充约定：未设置全局管理口令时保持兼容的开放模式，所有访问者按超级管理员处理；一旦设置口令，管理入口必须通过会话解锁。家庭管理员按成员逐个授权，不再假设一个家庭只能有一个 owner。家庭口令如果保留，只是该家庭的共享管理凭证；它不能替代成员登录 ID，也不能让一个家庭的令牌访问另一个家庭。

### 身份字段约定

- `member.id` 是服务端内部稳定 ID，只用于关联菜品作者、设备令牌和历史数据，用户不能手动填写，也不能因为改名而变化。
- `member.loginId` 是用户可见的登录 ID，在同一个家庭内唯一；允许汉字、英文字母、数字和常用符号，长度 1~32 个字符，拒绝控制字符和首尾空白。它不是数字 PIN。
- `member.password` 是个人验证口令，允许汉字、字母、数字和符号，长度 4~64 个字符；界面统一叫“密码”，不再暗示必须是数字。
- 为兼容现有数据，旧的 `pin` 字段迁移为个人密码；旧成员没有 `loginId` 时先用其显示名生成，重名时追加短后缀，管理员之后可以修改。
- 同一个家庭可以有多个 `role: owner` 成员。成员角色变更必须由当前家庭管理员或超级管理员完成，且服务端拒绝撤销最后一名 owner。
