# 买菜状态、菜谱复制与计划入口设计

日期：2026-10-17  
适用版本：1.21.0（提交 5dd584e）

## 1. 目标与问题范围

本轮修复围绕五个用户可见问题：

1. 买菜清单点“已买”或“入库”时误报“需要管理口令”；
2. 调料清单没有清楚区分家里已有、已经买完和仍待购买；
3. 共享菜没有明显的“复制到我的私房菜”入口，导致用户误以为一道菜只能在公开或私房之间二选一；
4. 本周计划中输入自定义菜名后，“加进去”按钮不可用或不会保存；
5. 最后一名家庭成员需要能明确解散家庭，并且不能再被旧家庭口令、成员密码流程干扰。

本设计同时收紧菜谱编辑权限：普通家庭管理员管理成员、家庭设置和做饭状态，但不自动获得修改别人菜谱的权力；菜谱由作者维护，超级管理员保留全局维护权。

## 2. 当前实现的根因

### 2.1 买菜清单误触发管理口令

public/app.js 的 toggle-shop、saveShoppingChecked 和批量勾选动作把已买状态写入 PUT /api/settings。服务端把 settings 视为超级管理员保护接口，因此普通成员只要勾选一项就会进入“管理口令”错误链路。库存接口 /api/pantry 本身允许已加入家庭的账户写入，错误来自状态保存接口而不是入库权限。

当前清单只根据库存条目渲染“家里有”，根据 S.shoppingChecked 加灰色样式，没有可持久化的家庭范围状态模型，也没有三段式分组。

### 2.2 共享菜与私房菜的语义不清

现有 /api/my-dishes/:id/adopt 已支持把共享菜复制到当前家庭，但前端 adoptBtn() 只有在已经选择家庭且当前账户属于该家庭时才显示。无家庭浏览共享菜单时用户看不到后续动作，已加入家庭时入口也只出现在部分卡片和详情场景。

前后端 canEdit / canWrite 仍把家庭管理员视为本家所有私菜的编辑者，并把共享菜的维护权授予任意家庭管理员。这与“作者维护、其他人复制”的使用习惯不一致。

### 2.3 自定义计划菜没有进入保存链路

openPlanPicker() 的按钮状态只读取 S.planPickSel 中的菜谱 ID；输入框 #planName 没有参与按钮启用判断。save-plan-picks 也只提交选中的菜谱 ID，未提交输入框文本，因此只输入“百香果酸汤牛肉”时必然被判定为“先勾几道菜”。

### 2.4 解散家庭入口与旧身份提示混杂

当前版本已有最后成员解散接口和账户设置入口，服务端会清理成员、申请、点餐、库存、计划、留言以及该家庭私菜。界面只在当前家庭设置中展示按钮，家庭首页和家庭卡片没有同样明显的入口；部分危险操作和旧帮助文案仍提到家庭口令或成员密码，容易让用户以为还需要第二套身份确认。

## 3. 推荐方案

### 3.1 买菜状态：新增家庭范围的状态资源

不继续把状态写入全局 settings，也不只写浏览器本地。新增家庭范围的买菜状态存储，按当前家庭和食材规范化名称保存：

~~~json
{
  "householdId": "house_xxx",
  "items": {
    "生抽": { "state": "completed", "updatedAt": "2026-10-17T08:00:00.000Z" },
    "冰糖": { "state": "needed", "updatedAt": "2026-10-17T08:00:00.000Z" }
  }
}
~~~

状态只允许 needed、completed 两种持久化值；available 不持久化，由当前家庭库存实时计算。展示优先级如下：

1. 库存中存在同名或可匹配条目，且总数量大于 0：已有；
2. 没有可用库存，但状态为 completed：已完成 / 已买；
3. 其余：待购买。

用户操作：

- “标记已买”：将状态设为 completed；
- “取消已买”：删除状态记录，回到待购买；
- “入库”：普通已加入成员即可调用 /api/pantry；成功后清除 completed 并立即显示为已有；
- 库存被消耗到 0 后，条目自动从已有回到待购买，除非用户再次标记已买；
- 提供“整理清单”按钮，一次按上述优先级重算分组；提供“清除已完成”按钮，不删除库存。

买菜页采用三个折叠分组：已有、待购买、已完成。默认展开待购买；每组显示数量和操作说明。普通成员、管理员和超级管理员都可以标记购买和入库；管理口令只保护全局设置、备份等明确的超级管理员操作。

建议接口：

- GET /api/shopping-status?householdId=...：读取当前家庭状态；
- PUT /api/shopping-status：更新一条或多条状态；
- DELETE /api/shopping-status?householdId=...&names=...：清理状态记录。

所有接口必须使用账户令牌校验家庭成员关系，不能接受客户端冒充的用户身份。解散家庭时一并删除该家庭状态。

### 3.2 菜谱模型：作者维护，复制形成独立副本

菜谱权限以全局账户 authorUserId 为主，以旧数据中的 authorId 作为迁移兼容字段：

| 菜谱 | 查看 | 编辑/删除 | 复制 |
|---|---|---|---|
| 我的私房菜 | 当前家庭成员 | 作者本人、超级管理员 | 可复制 |
| 别人的私房菜 | 当前家庭成员 | 作者本人、超级管理员 | 可复制（生成当前账户副本） |
| 共享菜 | 可见账户 | 原作者、超级管理员 | 已选择家庭时显示“收进我的私房” |
| 无作者历史菜 | 按原可见范围 | 仅超级管理员修复 | 可复制 |

家庭管理员仍可审批成员、管理家庭配置、更新做饭状态和处理家庭日常管理，但不因为 role: owner 获得别人菜谱的编辑权。超级管理员是账户级全局权限，不受当前家庭角色影响。

“收进我家”必须明确显示为复制动作：

- 菜卡、菜谱详情、菜单管理页均提供入口；
- 未选择家庭时点击入口先引导选择一个已加入家庭，不直接创建隐含归属；
- 复制后新记录的 householdId 是目标家庭，authorUserId 是当前账户；
- 原共享菜的内容、作者和状态完全不变；
- 副本详情显示“来源：共享菜单”，但后续编辑只影响副本。

旧数据迁移策略：能关联账户的菜谱补齐 authorUserId；无法关联的菜谱保持只读，提供复制和超级管理员认领入口，不继续使用“没有作者就放开编辑”的兜底。

### 3.3 本周计划：菜谱与临时菜可混合

计划弹层保留多选菜谱，同时把底部输入框定义为“临时菜名”。按钮启用条件为：至少选中一个未加入的菜谱，或输入非空临时菜名。

提交时：

- 每个选中菜谱提交 { dishId, name, servings }；
- 临时菜提交 { name }，dishId 为空；
- 两者可以在一次操作中混合提交；
- 输入框监听 input 事件，按钮文字显示“加 N 道进去”；
- 同一周按去除首尾空格、大小写不敏感的名称去重，重复项明确提示并保留其他成功项；
- 已存在于计划中的菜谱按钮继续禁用，但不影响临时菜提交。

### 3.4 家庭生命周期：退出与解散一致可见

家庭设置、账户首页的家庭卡片和当前家庭菜单都显示生命周期操作：

- 普通成员可直接退出；退出后清理当前家庭选择，回到账户首页；
- 唯一管理员但家庭还有其他成员时，必须先把至少一名成员设为管理员，之后才能退出；
- 最后一名成员且为管理员时显示“解散家庭”，而不是显示一个必然失败的“退出家庭”；
- 解散确认只使用明确的二次确认（家庭名称或确认按钮），不再要求家庭口令、成员密码或重新认领成员；
- 解散成功后删除家庭范围数据、申请、买菜状态和旧家庭会话，账户、其他家庭和全局超级管理员授权不受影响；
- 家庭不存在、已经解散或请求重复时，接口返回可理解的状态，前端回到账户首页而不是停留在空家庭页。

## 4. 页面与数据一致性

菜单首页、菜单管理、随机来一道、菜谱详情和计划选择器都使用同一份菜单投影。投影字段至少包含 id、name、category、householdId、authorUserId、作者显示名和 dishStatus。复制、编辑、删除或暂停供应成功后统一刷新投影，避免管理页和菜单页出现不同版本。

买菜页只使用当前家庭投影和当前家庭库存；切换家庭时清空上一家的买菜状态缓存，不得把 A 家的“已完成”带到 B 家。无家庭或浏览公开家庭时只读共享菜，不显示入库、计划和家庭买菜操作。

错误提示必须保留服务端真实原因：

- 未登录：提示登录账户；
- 未加入该家庭：提示先加入家庭；
- 无权编辑菜谱：说明作者和“复制到我的私房”入口；
- 超级管理员授权过期：只提示重新输入全局管理令牌；
- 买菜状态和库存写入失败：不得统一改写成“需要管理口令”。

## 5. 验收标准

### 买菜与权限

- 普通成员勾选“已买”、取消勾选和点击“入库”均不要求管理口令；
- 清单能分别显示已有、待购买和已完成三组；
- 库存数量大于 0 的食材自动进入已有；入库成功后立即从待购买/已完成移动到已有；
- 不同家庭的买菜状态互不影响，刷新和换设备后仍能看到服务端状态；
- 没有当前家庭时不显示家庭库存操作。

### 菜谱

- 普通家庭管理员不能编辑或删除别人的私房菜；
- 作者可以编辑自己的私房菜和自己发布的共享菜；
- 超级管理员仍可处理任意菜谱；
- 共享菜在卡片、详情和管理页都有明确的“收进我的私房”入口；
- 复制后修改副本不会改变共享源菜；
- 无作者历史菜不可被普通成员直接修改。

### 本周计划

- 只输入自定义菜名即可启用并保存；
- 选择菜谱和输入自定义菜名可以同时保存；
- 重复名称被明确提示，其他条目仍可成功加入；
- 临时菜不要求先创建菜谱。

### 家庭生命周期

- 最后一名成员在账户首页和家庭设置看到“解散家庭”；
- 解散后回到账户首页，账户和其他家庭不受影响；
- 唯一管理员有其他成员时不能直接退出，页面给出指定管理员入口；
- 所有家庭口令、成员密码和“再次认领成员”文案从新流程中消失。

## 6. 实现顺序与验证

1. 先新增家庭范围买菜状态接口和前端三组投影，修复口令误报；
2. 收紧前后端菜谱作者权限，补齐共享菜复制入口和迁移兼容；
3. 修复计划临时菜提交与去重；
4. 统一解散/退出入口和旧提示；
5. 运行：

~~~powershell
node --check server.js
node --check public/app.js
git diff --check
node _selftest.js
node build-package.js
node _packtest.js
node publish-selftest.js
~~~

6. 更新版本号，输出 E:/code/家庭菜单/package/家庭菜单-便携版/，提交并推送 GitHub，重启 http://localhost:8787/ 后按验收标准逐项测试。

## 7. 非目标

- 本轮不引入云端账户、短信、邮箱或远程找回密码；
- 不把家庭管理员自动升级为超级管理员；
- 不把共享菜直接改成当前家庭私菜；复制始终创建独立记录；
- 不立即删除旧接口，但新页面不再使用家庭口令或成员密码作为权限来源。
