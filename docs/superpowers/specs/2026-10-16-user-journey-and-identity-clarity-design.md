# 用户旅程与身份流程清晰化设计

**日期：** 2026-10-16  
**状态：** 已确认，等待实施计划  
**适用版本：** 当前 `1.14.0` 之后的下一次用户体验改版

## 1. 背景与目标

当前版本同时保留了两套身份流程：新设备先使用全局账户登录，登录后又可能进入“你是哪家的 / 你是谁家的成员”向导，再要求输入成员登录 ID 和成员密码。全局账户已经拥有稳定的 `userId`，继续要求设备重新认领成员会造成重复登录、身份容易串错，也让家庭申请看起来像匿名表单。

当前普通成员的设置页还是一整页连续内容，私菜、只读共享菜、家庭信息和账户操作混在一起；超级管理员已有折叠管理区，但普通成员没有同样的结构。家庭申请入口还要求用户输入家庭名称或 ID，普通账户实际上看不到未加入家庭的列表，名称查找也不能可靠解析。管理页与前面的菜单页还可能各自组装数据，导致分类、归属、作者或筛选结果不一致。

本次改版的目标是：

1. 全局账户成为新用户的唯一登录身份，登录后不再重复认领成员。
2. 家庭只保存成员关系和角色；账户的姓名由全局账户统一提供，用户切换家庭时自动得到对应角色。
3. 家庭申请由账户自动识别申请人，管理员能明确看到申请账户和全局账户姓名。
4. 普通成员和管理员使用一致的折叠式工作区结构，页面重点随角色变化。
5. 账号切换、换设备、申请状态和失效场景都不串身份、不丢状态。
6. 旧数据仍可使用，旧成员认领只作为一次性迁移兼容流程。

## 2. 已确认的产品决策

| 项目 | 决策 |
|---|---|
| 主身份 | 全局用户账户是唯一主身份，使用 `loginId + account password` 登录 |
| 家庭关系 | 家庭成员关系使用 `userId` 关联；同一账户在不同家庭可以拥有不同角色，但姓名始终来自同一个全局账户 |
| 登录次数 | 新用户每次进入只需要一次账户登录；不再进入成员选择和成员密码认领流程 |
| 旧数据 | 没有关联全局账户的旧成员只进入一次兼容绑定流程；新账户不显示旧向导 |
| 默认 ID | 注册留空时自动生成可修改 ID；注册成功后立即展示生成结果 |
| 显示名 | `account.displayName` 是全局权威姓名；同一账户在所有家庭、申请、点餐、留言、投票和菜品作者标签中使用同一个姓名 |
| 家庭申请 | 使用家庭邀请码或邀请链接定位目标家庭；不再依赖家庭名称搜索 |
| 申请人身份 | 服务端从账户令牌生成 `applicantUserId`，客户端不能伪造申请人 |
| 申请角色 | 默认普通成员，可申请家庭管理员；最终角色由目标家庭管理员决定 |
| 家庭上限 | 已加入的有效家庭最多 5 个，待处理申请不占名额 |
| 普通成员界面 | 使用与管理员一致的折叠组件，默认展开“我的私菜”，其余按用途分组 |
| 敏感操作 | 新账户使用账户密码重新验证，家庭管理员也可使用当前家庭口令；旧成员密码仅兼容历史数据 |
| 本地状态 | 家庭选择、折叠状态和申请缓存都按账户隔离；退出账户时清理当前账户的本地身份缓存 |

## 3. 当前问题审计

### 3.1 重复身份入口

`loadState()` 在账户登录后仍通过 `needWhoami()` 触发旧的家庭/成员向导。新账户因此要先输入账户 ID 和密码，再选择家庭、选择成员、填写成员登录 ID 和密码。`open-me` 也继续打开成员认领向导，即使当前账户已经通过 `userId` 匹配到了家庭成员。

改版后，账户登录成功直接使用账户关系设置当前家庭和角色。只有旧成员无法关联账户时才允许进入兼容绑定页，并在绑定成功后标记完成。

### 3.2 设备级缓存串身份

现有 `LS_MEMBER`、`LS_PENDING` 和 `LS_ONBOARD` 没有绑定账户。用户在同一设备退出账户 A 再登录账户 B 时，旧的成员选择、待申请姓名或向导完成状态可能继续影响账户 B。改版后这些状态必须按 `userId` 命名空间保存，或者在账户登录后统一迁移到 `familyMenu.accountState.<userId>`。

### 3.3 申请人身份不可靠

现有表单要求手填“你是谁”，服务端虽保存了 `applicantUserId`，管理页主要仍显示手填姓名。改版后申请记录至少保存：

```text
applicantUserId
applicantLoginIdSnapshot
applicantDisplayNameSnapshot
householdNameSnapshot
requestedRole
note
status
createdAt
updatedAt
```

账户令牌存在时，`applicantUserId`、登录 ID 快照和账户显示名快照由服务端写入；客户端只提交留言和申请角色。申请记录中的显示名快照只用于审计，当前页面展示应通过 `applicantUserId` 实时解析全局账户 `displayName`，账户改名后所有家庭中的当前显示同步更新。

### 3.4 目标家庭不可发现

普通账户的状态接口只返回已加入家庭，因此“输入家庭名称或 ID”既不能可靠查名称，也容易把内部 ID 暴露给用户。改版后每个家庭生成稳定的邀请码，并提供可复制的邀请链接。查码接口只返回家庭名称、图标和管理员公开显示名，不返回菜单、成员列表或家庭数据。

### 3.5 普通成员工作区缺少结构

普通成员当前看到连续的私菜、共享菜、分类、家庭设置和管理员入口，无法快速判断哪些内容能编辑。改版后所有角色都使用折叠组；折叠状态按账户和角色保存。

### 3.6 账户资料不完整

注册时自动生成的登录 ID 没有明确的成功提示和修改入口，也没有独立的账户显示名编辑入口。账户页应显示并允许修改登录 ID（需检查全局唯一）、显示名和头像；登录 ID 修改后旧 ID 立即失效，现有账户令牌保持有效。

### 3.7 凭证概念重复

新账户密码和旧家庭成员密码同时存在，敏感操作可能再次要求成员密码。新的账户流程统一使用账户密码重新验证；设置了家庭口令的家庭管理员也可输入家庭口令。旧成员密码只用于迁移期间验证旧成员，不能成为新账户的第二套日常登录身份。

### 3.8 申请状态反馈不足

当前账户工作区不突出显示待处理、已批准和已拒绝的申请。改版后账户首页和设置页都显示申请卡片，支持查看状态、撤回待处理申请、被批准后直接进入家庭，以及被拒绝后的重新申请。

### 3.9 菜单页与管理页数据来源不一致

当前菜单页和管理页可能分别过滤、补充作者或拼装私菜/共享菜，导致同一道菜在两个页面显示的名称、分类、标签、归属、作者或可见性不同；管理页修改后菜单页也可能要手动刷新才出现结果。改版后两页必须共用同一个当前家庭菜单数据投影和筛选上下文，以菜品 `id` 作为唯一对应键，所有增删改复制操作完成后立即失效并刷新该投影。

## 4. 统一身份模型

### 4.1 登录后状态

账户登录成功后，服务端返回当前用户资料和已加入家庭摘要。前端按以下顺序确定入口：

1. 账户令牌无效：显示登录页，不显示旧家庭数据。
2. 账户有效但没有家庭：显示“我的账户”首页，只提供创建家庭、输入邀请码申请加入和查看申请状态。
3. 账户已有家庭：选择上次使用且仍属于该账户的家庭；没有有效历史选择时进入第一户或家庭选择页。
4. 当前家庭关系存在：直接进入菜单首页，角色由关系计算。
5. 当前家庭关系不存在：不能通过本地缓存认领成员，只能回到账户首页或切换到已加入家庭。

### 4.2 顶栏身份入口

顶栏的“我是谁”改为当前账户显示名和当前家庭角色，例如“林阿姨 · 普通成员”。点击后显示：

- 账户显示名、登录 ID、头像；
- 当前家庭和当前角色；
- 已加入家庭列表与角色；
- 待处理申请；
- 修改账户资料、修改账户密码和退出登录。

不再显示成员选择网格。旧兼容绑定只有在账户资料标记为 `legacyUnlinked` 时出现，并明确标注“仅用于迁移旧家庭成员”。

### 4.3 全局账户姓名

`account.displayName` 是跨家庭、跨设备的唯一权威姓名；`loginId` 同样是全局账户属性。家庭成员关系只保存 `userId`、角色、状态和加入时间，不再保存可覆盖账户姓名的家庭专属称呼。点餐人、留言作者、投票人、菜品作者、申请人和成员列表都通过 `userId` 解析同一个 `displayName`，账户改名后所有家庭的当前显示同步变化。历史记录可以保留提交时的姓名快照用于审计，但不能把快照当作当前姓名。

## 5. 家庭申请与邀请流程

### 5.1 管理员生成邀请

家庭管理员在“家庭与成员”组中看到“邀请家人”。系统为家庭生成稳定的邀请码，并提供：

- 复制邀请码；
- 复制邀请链接；
- 重新生成邀请码（旧码立即失效，已有成员关系不受影响）。

邀请码不包含家庭口令，不可直接读取家庭数据。

### 5.2 用户提交申请

用户输入邀请码或打开邀请链接后，页面先展示目标家庭的名称和图标，再显示只读身份卡：

```text
申请账户：用户-AB12
账户显示名：林阿姨
```

用户只填写申请成为普通成员或家庭管理员，并可填写给管理员的留言。账户显示名和登录 ID 都是只读信息；如果用户需要更名，应先在账户资料中修改全局 `displayName`，不在申请表中创建家庭专属名称。

提交时服务端从 `X-Account-Token` 取得 `userId`，不接受客户端提交的 `applicantUserId`、登录 ID、账户显示名或任何家庭专属姓名字段。

### 5.3 管理员审批

管理员申请列表显示账户 ID、账户显示名、申请角色、留言和时间。审批操作为：

- 批准为普通成员；
- 批准为家庭管理员；
- 拒绝；
- 查看该账户是否已经达到 5 户上限。

批准成功后写入带 `userId` 的家庭成员关系，并保留申请记录的最终角色。申请人下一次刷新或打开账户首页时看到“已批准”，可直接切入该家庭。

### 5.4 申请状态

账户首页按目标家庭显示“待处理 / 已批准 / 已拒绝 / 已撤回”。同一账户对同一家庭只保留一条活动申请；待处理时再次提交更新留言或申请角色，而不是新增重复记录。

## 6. 角色工作区与折叠结构

### 6.1 普通成员

普通成员打开设置页看到以下折叠组：

1. **我的私菜**（默认展开）：新增、编辑、删除自己添加的私菜和私有分类。
2. **共享菜单**（默认收起）：只读浏览，提供“收进我家”。
3. **当前家庭**（默认展开）：家庭名称、当前角色、申请状态、切换家庭和邀请码申请入口。
4. **账户与帮助**（默认收起）：账户资料、密码、退出登录、管理员入口和权限说明。

普通成员看得到做饭状态、点餐、库存、计划和留言，但不能看到开做、完成、删除点餐或成员管理按钮。每个只读区域都说明维护者和下一步操作。

### 6.2 家庭管理员

家庭管理员沿用三组管理区：

1. 家庭与成员；
2. 菜单与日常数据；
3. 系统与备份（仅超级管理员可见完整内容）。

当家庭管理员没有输入家庭口令时，显示“当前为普通成员视角”和解锁入口；不能把账户登录成功误认为已经获得家庭管理员写权限。

### 6.3 超级管理员

输入全局管理口令后，账户在当前设备获得 12 小时超级授权。超级管理员看到所有家庭、成员、共享菜单、做饭状态、备份和平台设置；授权到期后页面自动回到原家庭角色。

### 6.4 折叠状态

折叠状态保存为账户级数据，例如：

```json
{
  "member": { "private": true, "shared": false, "household": true, "account": false },
  "admin": { "family": true, "menu": true, "system": true }
}
```

切换账户、退出登录或角色变化时不能沿用另一个账户的折叠状态。搜索命中某组时自动展开该组，清空搜索后恢复用户上次状态。

## 7. 数据、接口与安全边界

### 7.0 本轮权限收敛补充

- 全局管理口令未设置时，服务运行在“开放超级管理员”兼容模式：已登录账户和旧设备都可以进入管理区并初始化全局口令。设置口令后，必须先登录账户，再输入全局口令；成功后当前账户获得 12 小时超级管理员授权，失败时页面保留在当前视图并明确提示口令无效。
- 家庭口令不再是权限来源。历史 `house.pin` 字段可以继续被读取以完成迁移，但新代码忽略它；家庭管理员只由当前账户在该家庭中的成员关系 `role: owner` 决定，成员申请和管理员审批是唯一的家庭权限变更入口。家庭设置页不再显示家庭口令或解锁按钮。
- 账户属于某个家庭时，普通成员可以查看该家庭数据并维护自己的私菜；不能修改共享菜单、别人的私菜、成员、家庭设置、库存、计划、留言或做饭状态。做饭状态、点餐清理和其他管理动作由家庭管理员或超级管理员执行。
- 账户查看未加入的其他家庭时只返回共享菜单及公开家庭摘要，视图为只读；不能点菜、写留言、改库存、排计划、维护私菜或执行任何家庭操作。共享菜单中的菜品不能通过“收进我家”直接复制，用户如需私菜必须在自己已加入的家庭中手动新建。
- 管理页面的超级管理员、家庭管理员和普通成员都使用折叠工作区；折叠状态按账户和角色隔离。菜单页和管理页继续使用同一菜单投影，任何权限过滤都在投影层完成。

### 7.1 账户资料

新增或扩展账户资料接口：

- `GET /api/account/me`：账户资料、已加入家庭摘要、申请状态摘要；
- `PUT /api/account/profile`：修改登录 ID、显示名、头像；
- `PUT /api/account/password`：修改账户密码并撤销旧账户会话；
- `POST /api/account/verify`：用账户密码换取短期敏感操作凭证。

响应不返回密码、密码摘要、设备令牌或超级授权令牌。

### 7.2 邀请接口

- `POST /api/households/:id/invite`：管理员创建或刷新邀请码；
- `GET /api/invites/:code`：只读解析家庭公开资料；
- `POST /api/join-requests`：必须带账户令牌，服务端从令牌写入申请人身份；
- `GET /api/join-requests`：申请人只能看自己的，家庭管理员只能看自己管理的家庭，超级管理员可看全部；
- `PUT /api/join-requests/:id`：家庭管理员审批并选择最终角色；
- `DELETE /api/join-requests/:id`：申请人撤回自己的待处理申请，或管理员删除历史记录。

### 7.3 成员公开资料

普通成员的家庭数据只返回其他成员的全局 `displayName`、头像和角色。`loginId`、`userId` 和密码状态只返回给本人、该家庭管理员或超级管理员。服务端所有写接口都依据账户关系重新判权，不信任客户端传入的家庭成员 ID、角色、申请人 ID 或姓名。

### 7.4 菜单统一数据投影

菜单首页、菜单管理页、随机来一道、批量操作和菜品详情必须使用同一个 `menuProjection`，由当前账户、当前家庭、角色权限和菜单筛选条件共同计算。每个投影项至少包含：

```text
dish.id
dish.name
dish.category
dish.tags
dish.scope          shared | private
dish.ownerUserId
dish.ownerDisplayName
dish.visibility
```

统一投影必须保证：

- 相同 `dish.id` 在菜单页和管理页只对应同一条菜品记录，名称、分类、标签、共享/私菜归属和作者信息一致；
- 当前家庭过滤、私菜可见范围和角色权限只计算一次，管理页不能自行拼接第二套结果；
- 管理页新增、编辑、删除或复制成功后，通过统一缓存失效或事件刷新菜单页，刷新后立即看到相同结果；
- 管理页点击菜品打开与菜单页相同的详情数据和编辑前置值；
- 随机来一道和批量操作只能从当前投影中取数据，选择类别、标签、共享/私菜范围后仍使用同一套过滤规则。

### 7.5 旧接口兼容

`/api/claim`、成员密码和设备令牌保留一个迁移周期，但必须满足以下条件：

- 仅对没有关联 `userId` 的历史成员开放；
- 成功绑定后立即建立全局账户关系并标记完成；
- 新账户已有成员关系时拒绝进入旧认领流程；
- 新页面不提供旧接口入口，避免用户再次进入第二套登录。

## 8. 迁移与异常处理

### 8.1 本地状态迁移

登录账户后，把旧的设备级键迁移到当前账户命名空间：

- `LS_HOUSE` → `familyMenu.householdId.<userId>`，仅在该家庭属于账户时保留；
- `LS_MEMBER` → 只保留旧兼容绑定，正常账户不再读取；
- `LS_PENDING` → 由服务端申请记录替代，迁移后清理；
- `LS_ONBOARD` → 删除，改由账户关系和 `legacyUnlinked` 决定是否显示兼容页。

退出账户时清理当前账户的本地家庭选择、兼容成员选择和申请缓存，不影响其他账户的命名空间。

### 8.2 旧姓名与菜单数据迁移

- 旧家庭成员的 `name`、菜品的 `authorName` 和申请记录中的手填姓名只作为迁移快照保留；能关联 `userId` 的记录必须改为通过账户资料实时解析 `displayName`。
- 无法关联 `userId` 的历史记录可以继续显示原快照，并标记为“历史姓名”；完成兼容绑定后，后续页面统一显示新账户姓名。
- 迁移不得为同一账户在不同家庭创建多份姓名字段；成员关系只补齐 `userId`、角色、状态和时间信息。
- 菜单页与管理页都从同一菜单投影读取迁移后的菜品，迁移期间用 `dish.id` 去重，不能因作者字段变化生成重复菜品。

### 8.3 关键异常

| 场景 | 页面行为 |
|---|---|
| 账户会话过期 | 清空账户令牌，回登录页，并说明需要重新登录 |
| 没有加入家庭 | 显示创建家庭、输入邀请码和申请状态，不显示空菜单 |
| 邀请码无效或过期 | 显示错误原因和重新获取邀请码提示 |
| 已加入目标家庭 | 显示当前角色，禁止重复申请 |
| 达到 5 户上限 | 阻止创建/批准，并提示先退出一个家庭 |
| 家庭被删除 | 清理当前家庭选择，回到账户家庭页 |
| 申请被拒绝 | 保留结果，可重新提交新申请 |
| 最后一名管理员被删除或降级 | 服务端拒绝，并提示先指定新的管理员 |
| 旧成员无法关联账户 | 进入一次性兼容绑定页，成功后不再重复出现 |

## 9. 验证与验收标准

### 9.1 账户和身份

- 新设备只显示一次账户登录/注册表单。
- 注册留空 ID 时，成功页明确显示生成的 ID，并可修改资料。
- 登录后已有家庭时直接进入菜单，不弹成员选择和成员密码向导。
- 同一设备退出账户 A 登录账户 B，不显示 A 的账户姓名、待申请或成员选择。
- 同一账户在多个家庭切换时不需要重新登录或认领成员。
- 同一账户加入多个家庭时，所有家庭成员列表、申请记录、点餐、留言、投票和菜品作者位置显示同一个 `displayName`；账户改名后这些位置同步更新。

### 9.2 家庭申请

- 普通账户使用邀请码可以定位未加入家庭。
- 申请记录由服务端写入正确的 `applicantUserId`，客户端不能冒充别人。
- 管理员能看到申请人的登录 ID 和账户显示名，且该姓名与申请人加入其他家庭时的显示一致。
- 批准为成员或管理员后，成员关系立即可见且不重复创建。
- 申请状态在账户首页可见，撤回、拒绝、重新申请行为明确。

### 9.3 工作区和权限

- 普通成员页有四组折叠，私菜默认展开，共享菜单默认收起。
- 管理员页仍有三组折叠，搜索命中时只显示命中的组。
- 普通成员不能修改共享菜单、别人的私菜、做饭状态、成员和平台设置。
- 家庭管理员只能管理自己管理的家庭；超级管理员授权过期后自动降级。
- 未设置全局管理口令时，账户可进入开放管理模式并设置口令；设置后必须重新输入口令才获得超级管理员授权。
- 历史家庭口令不会授予任何新权限；家庭管理员身份只由 `role: owner` 关系和管理员审批产生。
- 未加入家庭的账户只能查看共享菜单，不能点菜、留言、库存、计划、私菜或“收进我家”。
- 普通成员不能提交点菜、修改库存/计划/留言或更新做饭状态；家庭管理员和超级管理员才可执行这些操作。
- 共享菜单只能浏览，不能直接复制进家庭；管理入口只对家庭管理员和超级管理员显示。
- 只读成员资料不包含其他人的登录 ID、`userId` 或密码状态。

### 9.4 菜单与管理页一致性

- 菜单页、管理页、随机来一道、批量操作和菜品详情对同一个 `dish.id` 显示相同名称、分类、标签、共享/私菜归属和作者姓名。
- 当前家庭、类别、标签和可见性筛选在两个页面得到完全相同的结果；普通成员只看到有权访问的投影项。
- 管理页新增、编辑、删除、复制后，菜单页刷新立即反映相同结果，不能出现一页有、一页无或字段不同。
- 管理页打开的菜品详情与菜单页详情使用同一数据对象，随机来一道只能从当前统一投影抽取。
